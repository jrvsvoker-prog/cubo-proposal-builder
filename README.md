# Cubo Proposal Builder

Папка для сборки персонального интерактивного коммерческого предложения:
менеджер присылает агенту обычное сообщение о компании — агент возвращает
один HTML-файл, где клиент видит свой бизнес на шести живых экранах Cubo.

Анкеты, формы и ручная правка данных не нужны. Промежуточные шаги агента
утверждать не надо — при достаточных вводных он идёт до результата сам.

## Что потребуется

- Компьютер с Node.js (версия — в `portable-manifest.json` → `runtime`)
  и доступом в интернет для первой установки зависимостей.
- Среда с агентом, у которого есть доступ к файлам и командам
  (Codex, Devin, Cursor, Claude Code — любая). Откройте в ней эту папку
  как рабочую.
- Для полной визуальной проверки агенту нужен браузерный инструмент.
  Если он недоступен или запрещает отдельный способ открытия, агент
  перечисляет непроверенные критерии. Ограничения исследования бренда
  обрабатываются по регламенту.
- Полезно, но не обязательно: сайт компании, прайс, файл логотипа
  (PNG или SVG).

## Как получить папку

- ZIP-архив: распакуйте в любое место. Git для работы не нужен.
- GitHub: `git clone https://github.com/jrvsvoker-prog/cubo-proposal-builder.git`
  (репозиторий приватный, доступ выдаёт владелец).

## Как запустить

1. Откройте папку в среде с агентом.
2. Напишите агенту сообщение о компании в свободной форме, например:

   > Собери КП для сети автошкол «Вектор»: 6 филиалов по городу,
   > сайт vektor-drive.example.ru, прайс от 38 000 за курс. Логотип лежит
   > в папке `client-materials/logo.svg`. Цвет бренда — с сайта.

   Чем больше фактов (услуги, филиалы, цены, логотип, партнёр, текст
   предложения, смета работ), тем точнее результат. Недостающее агент
   ищет сам или помечает допущением.
3. Агент пройдёт цепочку: вводные → исследование → сводка → роли и
   Job Stories → профиль → сборка → проверка → HTML.
4. Результат сборки — `dist/<slug>/index.html`, один файл для передачи.
   Агент сообщает результаты проверки и отдельно статус открытия без
   сервера (`file://`). Если оно не проверено, этот критерий остаётся
   открытым до проверки точного файла.

## Границы

- Две модели бизнеса: обучение/абонементы (`school`) и заявки/заказы
  (`service`). Другие ниши собираются на ближайшей модели с допущением;
  если подходящей модели нет вовсе — агент задаст один короткий вопрос,
  а не предложит заведомо неподходящий шаблон.
- Числа в демо синтетические — правдоподобные, но не реальные данные
  клиента. Реальными остаются названия, структура и цены из вводных.
- Шесть экранов и их композиция фиксированы: меняется содержание,
  не механика шаблонов.
- При неизменных сводке, входных файлах и версии Builder повторная
  генерация даёт побайтно тот же профиль.

## Устройство папки

| Что | Зачем |
|---|---|
| `AGENTS.md` | инструкция для агента — читается автоматически |
| `docs/dynamic-proposal/agent-runbook.md` | единственный действующий порядок действий |
| `docs/dynamic-proposal/data-contract.md` | какие поля сводки реально попадают в КП |
| `docs/dynamic-proposal/runs/` | материалы прогонов; примеры `mehanika` и `mayak-mvp` |
| `examples/` | проверенный образец HTML одной из синтетических компаний |
| `src/`, `vendor/cubo/`, `scripts/` | шаблоны экранов, генератор и сборка |
| `portable-manifest.json` | состав папки, версии среды и контрольные суммы |

Вопросы и замечания — команде Cubo. Публикация собранных КП и самой папки
не входит в этот сценарий.
