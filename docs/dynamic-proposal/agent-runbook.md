# Регламент агента: сообщение → готовое динамическое КП

Работай из корня этой папки. Цепочка одна: входное сообщение →
`docs/dynamic-proposal/runs/<slug>/summary.json` →
`src/data/profiles/<slug>.json` → проверка → `dist/<slug>/index.html`.
Продуктовую логику и границы шаблонов объясняет
[builder-pipeline.md](builder-pipeline.md); этот файл — единственный
технический порядок действий.

## Границы работы

- Для одного нового КП разрешены только его `docs/dynamic-proposal/runs/<slug>/`,
  `src/data/profiles/<slug>.json`, регистрация в
  `src/data/profiles.typecheck.ts` и `dist/<slug>/`. Не меняй шаблоны экранов,
  стили, `vendor/`, генераторы, архетипы, другие профили и чужие запуски.
- До генерации проверь, что целевой slug не занят. Не перезаписывай профиль,
  run или сборку другого клиента и ничего не удаляй ради нового КП.
- Не делай merge, push, публикацию или deploy. Локальная сборка остаётся
  локальным артефактом.

Это MVP для двух архетипов: `school` и `service`. Шесть принятых шаблонов не
меняются. Экран 04 показывает данные в пайплайне, таблице и карточках; действий
над записью в нём нет.

## 0. Подготовить среду при первом запуске

Для распакованной выдачи проверь Node.js и npm: версии проверенной среды
указаны в `portable-manifest.json` → `runtime`. Если зависимости ещё не
установлены, выполни из корня этой папки:

```bash
npm ci
```

Для первой установки нужен интернет. `node_modules` в выдачу не входит;
повторять установку для каждого КП не нужно. Не изменяй package.json и
package-lock.json ради установки.

## 1. Принять вводные и зафиксировать смысл

Вход — свободное сообщение в чате. Нужны название, чем компания зарабатывает и
какая единица продажи. Primary агент выясняет сам; переданный менеджером
цвет имеет приоритет. Полезны сайт, названия и число подразделений,
номенклатура, прайс, файл логотипа, данные о партнёре и текст/смета предложения.

Промежуточные утверждения сводки, джобов и продолжения не требуются: при
достаточных вводных иди по шагам без остановок. Короткий вопрос нужен только
при существенной неясности адресата, предмета предложения или бизнес-модели
(что является одной продажей — чек, заказ, абонемент), которую нельзя
разрешить из доступных материалов. Отсутствие сайта, логотипа, отдельной
сметы или доступа к поиску остановкой не является — фиксируй допущения в
`assumptions` и продолжай.

Формулируй вопрос открыто, без выбора из поддержанных шаблонов. Например,
на «Собери КП для нашей компании “Горизонт”»: «Чем занимается “Горизонт”
и что вы предлагаете клиентам?» Не спрашивай «обучение или заказы на работы?»:
это подгоняет неизвестный бизнес под два архетипа. После ответа сохрани факты
и продолжай; подтверждённое не переспрашивай. Если из ответа ясно, что оба
архетипа не подходят, назови ограничение, а не меняй смысл бизнеса.

Выбери `slug`: строчные латинские буквы, цифры и дефисы по
`^[a-z0-9][a-z0-9-]{0,63}$`. Он станет именем профиля и папки сборки.

Архетип выбирай по единице продажи:

| Модель | Архетип |
|---|---|
| абонемент, группа, обучение | `school` |
| заявка или заказ с выполнением и сроком | `service` |

Ниша вне двух моделей требует выбора ближайшей из них с явным допущением;
новый архетип не создавай. Если ближайший архетип заведомо не подходит
бизнесу — это тот самый короткий вопрос, а не принудительный выбор.

Из внешних источников бери реальные названия компании, подразделений и
услуг. Цены из действующего прайса можно использовать как входной диапазон,
но все суммы, показатели, обращения и дельты в демо синтетические. Они не
доказывают реальные обороты, загрузку или число клиентов. Ссылки на источники
и допущения сохраняй в материалах `docs/dynamic-proposal/runs/<slug>/`.

### 1.1. Обязательно определить primary

До подготовки готовой сводки выполни
[проверку бренда и выбор цвета](#primary-и-монохромный-логотип).
Сохрани решение в `docs/dynamic-proposal/runs/<slug>/research.md`. Отсутствие записи означает,
что шаг не выполнен: к генерации не переходи. Если сайта или доступа нет,
зафиксируй конкретное ограничение и выбери запасной цвет по правилам ниже;
вопрос менеджеру и его подтверждение для этого не нужны.

## 2. Подготовить машиночитаемую сводку

Сохрани JSON в `docs/dynamic-proposal/runs/<slug>/summary.json`.
`profile-draft.mjs` читает JSON, не YAML. За образцы возьми
[runs/mehanika/summary.json](runs/mehanika/summary.json) и авторский
MVP-прогон [runs/mayak-mvp/summary.json](runs/mayak-mvp/summary.json).
[Результат прогона](runs/mayak-mvp/result.md) показывает проверки
и ограничения данных.

Минимальный контракт:

```json
{
  "company": {
    "name": "Орион",
    "displayName": "Школа «Орион»",
    "slug": "orion",
    "brand": { "primary": "#4f46e5" }
  },
  "archetype": "school",
  "units": { "kind": "Филиал", "names": ["Речной", "Лесной"] },
  "customer": {
    "singular": "Родитель",
    "entity": "Ученик",
    "entityExample": { "name": "Ученик № О-12 · Семья" }
  },
  "offer": {
    "itemNoun": "Занятие",
    "items": ["Робототехника"],
    "priceRange": [4000, 8000]
  },
  "deal": { "noun": "Заявка", "pipeline": ["Новая", "Пробное занятие", "Договор", "Активна"] },
  "time": { "demoDate": "2026-09-16" },
  "scale": { "monthlyDeals": 80 },
  "assumptions": ["Материалы бренда не переданы. Фиолетовый #4f46e5 предложен из палитры для образовательного примера; это не подтверждённый цвет клиента."],
  "characters": {
    "staff": { "name": "Вера Полякова", "role": "Куратор" },
    "colleague": { "name": "Роман Белый", "role": "Преподаватель" },
    "client": { "name": "Нина Громова", "role": "родитель" }
  }
}
```

`deal.pipeline` содержит ровно четыре непустые стадии; `offer.items` не пуст;
`priceRange` — ровно два неотрицательных числа, первое не больше второго
(равные значения — фиксированная цена); `demoDate` и
`customer.entityExample.dueDate` — реальные календарные даты `YYYY-MM-DD`;
`scale.monthlyDeals` — положительное число; `units.names` — список (пустой
допустим, выдуманные подразделения при этом не создаются). `characters`
необязателен: без него профиль получает нейтральных демо-персонажей. Все
предположения пиши строками в `assumptions`, включая типовые названия,
диапазон цен и выбор ближайшего архетипа.

Партнёр по умолчанию — интегратор RAND: каждое КП включает
`proposal.partner = { name: 'RAND' }` без поля `logo`. Знак — только
шаблонный SVG `src/assets/brands/rand-logo.svg` (первый квадратный с рамкой):
он инлайнится и красится под фон. Файл из сводки RAND не подменяет.
Опускать партнёра только по явному указанию «без партнёра».
Чужой интегратор — другое имя и свой файл в `proposal.partner.logo`.

Масштаб демо. Если на сайте линейка (вкусы, услуги, позиции каталога),
в `offer.items` ставь 3–6 реальных названий с сайта. Первая позиция —
сквозной пример карточки, остальные видны в структуре, заказах и подборке.
Не схлопывай ассортимент в один SKU: один столбец на 100% в «Структуре»
не сдавать. Если позиций меньше трёх, допиши демо до трёх-четырёх
(первая с сайта, остальные типовые для деятельности) и пометь выдумку
в `assumptions`. Одна услуга допустима, только когда у бизнеса правда
одна позиция, как у «Маяка».

### Что реально читает генератор

| Поля summary | Результат |
|---|---|
| `company.name`, `displayName`, `slug`, `company.activity` | имя, тексты, адреса и деятельность; генератор KPI использует `displayName` как сид |
| `company.brand.primary` | `--client-primary` во всех экранах; в новом запуске агент задаёт цвет явно после шага 1.1. Технический fallback старых сводок без поля — `#4f46e5` |
| `company.brand.logo` | локальный PNG/SVG рядом со сводкой → data URI; без поля — буквенный fallback |
| `company.brand.coverPlate` | необязательно `true`: цветной знак на обложке на плашке, без инверсии; иначе белый фильтр без плашки |
| `archetype` | допустимы только `school`/`service`; задаёт метрики, масштабы и период аналитики |
| `units.names`, необязательный `units.kind` | фильтры и подписи; при пустом списке — метрики всей компании без выдуманных подразделений |
| `customer.singular`, `entity`, `entityExample.name`; необязательные `subject`, `dueDate`, `examples`, `unit`, `fields[]` | лексика, главный пример, поля карточки, даты и список демо-записей; `subject` не повторяет позицию прайса |
| `offer.items`, `priceRange`; необязательный `itemNoun` | направления, подборка и демонстрационные суммы, зажатые в диапазон после округления |
| `deal.noun`, `pipeline` | подписи и четыре стадии |
| `time.demoDate` | даты демо и год аналитики |
| `proposal.intro` | интро-текст обложки вместо шаблонного подзаголовка |
| `proposal.partner { name, logo? }` | пара «партнёр × клиент»; по умолчанию `{ name: 'RAND' }` без `logo` — шаблонный SVG красится сам; `logo` только у другого интегратора; опускать партнёра только по явному «без партнёра» |
| `proposal.estimate { title?, text?, rate?, items[], total? }` | коммерческий блок между главами и финалом; заменяет базу из `src/data/estimate-defaults.json` целиком, без смешения позиций; `rate × hours` обязано сходиться с суммами |
| `jobs { main, roles[] }` | метрики историй собирают `dashboard.defaultMetrics`; `result` истории с экраном `03` → ответ в истории карточки, с `06` → `portal.upcoming[1]`; первый результат на слот выигрывает; без 03/06 результат опускается с предупреждением |
| `assumptions` | текст `dashboard.assumptions` |
| `characters.staff`, `colleague`, `client` | имена и роли в карточке, подборке и кабинете |

Генератор передаёт `scale.monthlyDeals` и `offer.priceRange` в профиль, и
модель дашборда/аналитики использует их в расчётах. Он не читает
`scale.avgDeal`, `archetype_assumption`,
`units.assumption`, `company.brand.site`, `customer.entityExample.chips`,
`offer.priceUnit` и любые дополнительные поля. Их можно хранить для объяснения
решения, но не обещай их влияния на HTML. `jobs.main` и формулировки
`when/want/so` остаются в сводке и карте джобов — в HTML не дублируются.

Полная карта полей и валидационные границы — в
[data-contract.md](data-contract.md). Маршрут «джоб → экран → поле» — в
[builder-pipeline.md](builder-pipeline.md).

### Primary и монохромный логотип

Это обязательный шаг агента, а не автоматический поиск генератора.

1. **Проверь переданные материалы.** Явное пожелание менеджера имеет приоритет,
   затем — основной акцент из официального брендбука. Сохрани источник цвета.
   Явно заданный монохромный вариант сохраняй; не заменяй его палитрой.
2. **Если цвет не задан, исследуй сайт.** Открой главную страницу и страницу
   нужного направления, даже если менеджер прислал только вторую. Посмотри
   основные кнопки, ссылки и активные элементы; проверь повторение акцента
   в разных местах. Дойди до содержимого и нижней части страницы, не
   ограничивайся первым экраном. Для видимого элемента возьми точный цвет
   из вычисленного стиля или связанного CSS, если инструмент это позволяет,
   и сверь с изображением страницы. Цвет из CSS без видимого применения
   не является доказательством. Запиши URL, элемент и найденное значение;
   приблизительный подбор по изображению обозначай как приближение.
3. **Отдели акцент от оформления.** Чёрный/белый логотип, тёмный фон,
   случайная фотография, рекламный баннер или индикатор ошибки не определяют
   primary. Если на профильной странице акцента нет, это ещё не результат
   проверки всего сайта. При нескольких акцентах используй повторяющийся
   цвет основного действия выбранного направления и объясни выбор.
4. **Если подтверждённого цвета нет, выбери один из палитры ниже.** Это
   допустимо после проверки доступных материалов или при конкретном
   ограничении: сайт не передан, не найден, не открывается, доступ к браузеру
   отсутствует. «Не удалось проверить» и «в проверенных местах акцент не
   найден» — разные результаты. Не выдавай одно за другое. Выбирай по
   характеру бизнеса и доступным визуальным материалам, без жёсткой привязки
   отрасли к цвету. Если ориентиров нет — синий `#0369a1`.
5. **Зафиксируй решение и примени его явно.** Заполни запись ниже в
   `research.md`, затем `company.brand.primary` в сводке. Выбор из палитры
   отметь в `assumptions`: «Для КП предложен …; фирменный акцент не
   подтверждён». Не оставляй поле пустым, полагаясь на технический fallback.

| Вариант | Primary | Возможный ориентир, не обязательная отрасль |
|---|---|---|
| Синий | `#0369a1` | универсальный вариант, услуги и B2B; выбор без иных ориентиров |
| Фиолетовый | `#4f46e5` | образование, цифровые и творческие услуги |
| Бирюзовый | `#0f766e` | сервис, здоровье и уход |
| Зелёный | `#15803d` | природа, сад, экологические проекты |
| Красный | `#b91c1c` | спорт и активный отдых |

Запись в `research.md` обязательна для каждого нового КП:

- **Источник:** сообщение менеджера, файл/раздел брендбука или точные URL.
- **Проверено:** страницы и конкретные кнопки/активные элементы; либо причина,
  по которой проверка недоступна. Не отмечай непосещённую страницу проверенной.
- **Результат:** заданный цвет / найденный акцент / акцент не найден в
  проверенных местах / проверить не удалось.
- **Решение:** выбранный hex, источник или название варианта палитры и причина
  выбора; подтверждённый цвет, приближение или предложенное оформление.
- **Сверка после сборки:** тот же цвет в summary, `theme.primary` профиля
  и готовом HTML; обложка, графики, активное меню и кнопки просмотрены.

Перед генерацией нужны первые четыре пункта, перед выдачей — все пять.
Не заменяй запись галочкой «бренд проверен» без источников. Если пропущен
поиск или значение не совпало, вернись к этому шагу, исправь сводку и
перегенерируй профиль. Для «Мосгорбайка» правильный результат — найденный
на главной акцент кнопок `#3633cd`, а не серый цвет логотипа или палитра.

Палитра меняет только primary. Сохраняй значения success/danger/warning и
цвета логотипа. В готовом HTML акцент и текст на нём должны читаться;
проверка логотипа выполняется отдельно. Успешная сборка этого не доказывает.
Генератор проверяет формат hex, но не достоверность исследования: обязательную
проверку выше выполняет агент, а не менеджер.

### Логотип клиента и партнёра

Это жёсткий канон. Нарушение возвращает уже отвергнутый вид: плашка всем
знакам или RAND, съеденный фильтром. Не обходи правило «под конкретного клиента».

**RAND (партнёр по умолчанию).** Всегда наш первый квадратный знак с рамкой:
`src/assets/brands/rand-logo.svg`. Он SVG, инлайнится в шапку, красится через
`currentColor`: тёмный фон → светлый знак, светлый фон → тёмный. Плашки нет.
CSS-фильтр (`brightness` / `invert`) ставить нельзя: он съедает рамку.
Поле `proposal.partner.logo` при имени RAND запрещено. Не подменяй этот SVG
перерисовкой, PNG, `<img>` или чужим файлом из сводки.

**Клиент.** Один файл `company.brand.logo` на все места. По умолчанию плашки нет:
на тёмной обложке монохромный/тёмный знак становится белым CSS-фильтром, внутри
экранов остаются исходные цвета. Если инверсия портит знак (цвет, фото, белые
детали внутри) — это не блокер: поставь `company.brand.coverPlate: true`. Тогда
на обложке исходные цвета на светлой плашке, внутри экранов по-прежнему без
плашки. Плашка — запасной выход для клиента, не шаблон и не норма для RAND.

`company.brand.logo` — путь к файлу относительно `summary.json`: PNG или SVG.
Файл встраивается как data URI — готовый HTML автономен. Отклоняются до записи
профиля: абсолютные пути, URL, `file:`/`data:`-строки, `..` в пути, другие
форматы, а также SVG с внешними ресурсами, скриптами и импортами. Нет логотипа
клиента — буквенный fallback, это нормальный сценарий, не ошибка.
`proposal.partner.logo` — только если партнёр не RAND.

Перед записью пути в сводку выполни подготовку ниже. Генератор только проверяет
формат и встраивает файл: он не удаляет фон и не оценивает качество изображения.

1. **Найди лучший исходник.** Сначала официальный SVG или PNG с прозрачностью.
   Нет SVG — попробуй выделить знак из PNG/скрина в поддерживаемый PNG, сохранив
   пропорции. Не дорисовывай знак, не воссоздавай генерацией, не выдавай
   увеличение маленькой картинки за качество. Недоступный поиск не блокирует
   сборку.
2. **Посмотри, что является фоном.** PNG не доказывает прозрачность. Отличай
   фон страницы от белых деталей знака, фирменной плашки, обводки и просветов
   в буквах. Не удаляй все белые пиксели.
3. **Убери только посторонний фон** в отдельной копии, если знак отделяется
   уверенно. Сложный фон, ореол, рваные края — ищи другой оригинал; если его
   нет, оставь пригодный исходник и для обложки используй `coverPlate`.
4. **Цвет.** По умолчанию сохраняй фирменные цвета файла. RAND красится сам.
   Клиента не подгоняй под `primary`. Многоцветный знак, градиент, фото или
   эмблему с белыми внутренними элементами не инвертируй: ставь `coverPlate`.
5. **Не меняй CSS и шаблоны ради одного клиента.** Для плашки на обложке есть
   только `coverPlate`. Других полей светлый/тёмный нет. Если хорошего файла
   нет — опусти `logo`, оставь название, используй буквенный fallback.
6. **Проверь итог в готовом HTML** на 1440 и 390: обложку, пару RAND × клиент,
   открытое и компактное меню, подборку, вход и кабинет. Знак узнаваем, не
   обрезан, не на плашке там, где она не нужна. Сборка без просмотра не считается
   проверкой.
7. **Запиши решение** в `runs/<slug>/`: источник, SVG или нет, инверсия или
   `coverPlate`, где проверено. В `summary.json` — относительный путь к файлу.

Ориентиры: прозрачный монохром → инверсия на обложке; цветной SVG/PNG →
`coverPlate`; нет SVG, знак не отделяется → `coverPlate` или fallback.
Логотип сам по себе не повод останавливать КП вопросом менеджеру.

### Карточка: описание, параметры, телефон

КП показывает рабочий пример B2B-учёта, не пустую карточку с одним странным полем.

- **Описание** (`customer.entityExample.subject`) — что делается по этой записи:
  объект, состав работ, повод. Не копируй название услуги из `offer.items`.
  Генератор отклонит сводку, где описание совпадает с позицией прайса.
- **Параметры бизнеса.** Возьми 1–4 факта с сайта или из вводных: точка,
  объект, договор, модель, офис. Одна точка в `units.names` попадает в карточку
  сама. Несколько точек — укажи `entityExample.unit` из этого списка.
  Остальное — `entityExample.fields: [{ label, value }]`. Не дублируй услугу,
  имя клиента и описание.
- **Телефон.** Генератор сам ставит правдоподобный демо-номер по slug.
  Не пиши `+7 000 000-00-00`.

- **Сквозной пример.** Первая позиция `offer.items` — это заказ карточки.
  Имя записи, описание, лента и кабинет говорят про неё, а не про другой
  вкус или услугу из списка. Описание: пометка к этому заказу (объём, объект,
  состав работ), не второе название позиции и не чужой SKU.

### Тексты оболочки

Шапка уже говорит, кому предложение (`brand.note`). Кикер «Для …» на обложке
не показывать: это дубль. В клиентских текстах не ставь длинное тире (—):
перефразируй, поставь точку или двоеточие. Диапазоны дат — короткое тире (–).
Пустая величина в таблице может остаться знаком «—».

`proposal.intro` описывает бизнес целиком простым русским: кто клиенты
и что происходит в примере ниже. Не пиши «пример ниже про один SKU», если
на экранах весь процесс. Без необъяснённых англицизмов (HoReCa и подобное).
Генератор отклонит интро с длинным тире.

### Jobs: роли и Job Stories

В `characters.*.role` пиши короткую подпись для интерфейса, обычно 1–2 слова.
Убирай уточнение, уже понятное из бизнеса: «Администратор мастерской» →
«Администратор». Сохраняй смысл должности: «Главный бухгалтер» нельзя
механически сокращать до первого слова. Полную роль можно оставить в `jobs`.
Проверь подписи в готовом HTML, прежде всего в узком меню: ключевая роль
должна читаться целиком. Если подпись обрезана, сначала сократи её осмысленно
в сводке и пересоздай профиль; не уменьшай шрифт и не меняй шаблон ради неё.
Случай, где смысл нельзя сохранить короткой подписью, явно отметь для ревью.

Необязательный блок. `jobs.main` — один главный джоб (внутренний, в профиль
не пишется). 1–4 роли, у каждой 1–3 истории `when`/`want`/`so` плюс
необязательные `metrics`, `screens`, `result`. Метрики — только из библиотеки
выбранного архетипа (`src/data/archetypes.json`); экраны — только `01`–`06`.
Неподдержанная метрика или экран — отказ сводки до записи. Правило набора
KPI: поддержанные метрики историй идут первыми в порядке первого упоминания
(повторы считаются один раз), затем следуют базовые метрики архетипа, которых
ещё нет. Предела «ровно четыре» нет; при пяти–шести карточках проверь их
читаемость в браузере на 1440/1024/390 и не подменяй выбор клиента дефолтными
метриками ради сетки.

### Масштаб, цены и прогресс в содержании

- `offer.priceRange` задаёт демонстрационные суммы записей, оплат и подборки;
  масштаб (`scale.monthlyDeals`) и диапазон передаются в модель дашборда и
  аналитики и участвуют в расчёте KPI.
- Прогресс кабинета и карточки синхронизирован со стадиями:
  `portal.children[0].sub` показывает «Этап N из 4» по позиции стадии в
  `deal.pipeline`.

### Смысловая сверка до выдачи

До генерации сопоставь сообщение и сводку: кто клиент, что он продаёт,
как называются предложение, покупатель и запись, какие подразделения
действительно указаны. Архетип выбирается после этого. Отсутствие сведений
не превращай в утверждение об отсутствии: «филиалы не названы» не означает
«филиалов нет». Не создавай подразделения, тарифы и процессы для заполнения
шаблона. Допущения записывай явно; при недостатке деталей используй нейтральный
текст. Менеджер не подтверждает эту внутреннюю сверку и не редактирует сводку.

После генерации проверь следующие связи в профиле, затем в готовом HTML:

| Что сверить | Какой результат допустим |
|---|---|
| `units.names` → `units`, глава 01 и фильтр 02 | Только указанные подразделения; пустой список → показатели компании, без выдуманной сети |
| `offer.items`, `offer.itemNoun` → направления 02/04 и свойство 03 | Те же предложения и термин из сводки; без `itemNoun` — «Предложение» |
| `deal.pipeline` → стадии, следующие шаги 04 и прогресс 03/06 | Следующий шаг ссылается на следующую стадию; лексика автосервиса не переносится в школу |
| `analyticsConfig.programs` и `sources` → разрезы 02 | Синтетические типы обращений и источники не выдаются за исследованные тарифы, каналы или процессы клиента |
| Главный пример 03–06 | Один клиент/предмет, согласованные стадия и сумма; предоплата + остаток = общая стоимость |
| Логотип и коммерческая оценка | Обработка проверена по правилам выше; смета менеджера сохранена без смешения с базой |

Генератор не получает тарифную классификацию из сводки: по умолчанию в 02
используются нейтральные «Первичное обращение» и «Повторное обращение».
Не добавляй вымышленные поля сводки, чтобы якобы настроить неподдержанный разрез.
Непереданный сайт не доказывает его отсутствия; если вводные явно противоречат
синтетическому примеру на экране, этот случай требует корректировки до выдачи.

Если ошибка в сводке — исправь её по вводным и перегенерируй профиль. Если
ошибка в шаблоне/генераторе, зафиксируй вход и неверный результат для исправления
Builder; не маскируй её ручной правкой готового JSON и не объявляй КП готовым.
Тесты, `validateProfile` и typecheck не понимают весь смысл свободного сообщения.
В результате запуска кратко назови выполненную смысловую проверку и ограничения.

## 3. Сгенерировать готовый профиль

До команды проверь запись о primary по шагу 1.1 и явное значение в сводке.
Если их нет, сначала заверши выбор цвета. Не подставляй запасной вариант
лишь для того, чтобы обойти исследование доступного сайта.

Обычный путь сразу пишет готовый профиль без ручных слотов и без копирования
`school.json` либо `service.json`:

```bash
node scripts/profile-draft.mjs docs/dynamic-proposal/runs/<slug>/summary.json --out src/data/profiles/<slug>.json
```

Команда сначала валидирует сводку, затем профиль через `validateProfile()` и
только после этого записывает файл. Ошибочная сводка не перезаписывает
существующий результат. Не редактируй сгенерированный `profile.json` вручную:
исправь `summary.json` и запусти команду снова. Повторный запуск с тем же
входом даёт байт-в-байт тот же файл.

`--draft` — сохранённый технический исторический режим; он намеренно создаёт
`[ ЗАПОЛНИТЬ: … ]` и не является штатным обходом готовой сборки. Не переноси
его результат в рабочий профиль.

Зарегистрируй новый готовый JSON для TypeScript в
`src/data/profiles.typecheck.ts`. Для имени файла используй slug, для
TypeScript — допустимый camelCase-идентификатор:

```ts
import mayakMvp from './profiles/mayak-mvp.json'
const _mayakMvp: ProposalProfile = mayakMvp
void _mayakMvp
```

Это регистрация проверки, а не ручная доработка данных профиля. Поля `id` и
`initials`, сформированные скриптом, не удаляй: они зарезервированы контрактом.

## 4. Проверить и собрать

Все команды выполняй из корня папки:

```bash
npm run typecheck
npm run test
npx vite build --mode <slug> --outDir dist/<slug>
```

`npm run test` проверяет генератор и зафиксированные профили, а `npm run
build:all` собирает только `school` и `service`; ни одна из них не заменяет
клиентскую команду `vite build --mode <slug>`. Последняя повторно читает и
валидирует `<slug>.json` через `vite.config.ts`, а `vite-plugin-singlefile`
включается только при сборке: результат — один `dist/<slug>/index.html`.

Для визуальной проверки можно запустить профиль по HTTP:

```bash
npm run dev -- --mode <slug> --host 127.0.0.1 --port 5215 --strictPort
```

Проверь 1440, 1024 и 390: шесть глав, название и primary, реальные названия
услуг/подразделений, согласованность главного демо-примера в 03 → 04 → 05 → 06
с учётом известных ограничений выше, три вида Data View и пустую выдачу
поиска, а также отсутствие действий над записями в 04. Проверь консоль и
отсутствие следов другого профиля в HTML известными строками из источника.
Сверь primary с записью в `research.md`, сводкой и профилем; дополни пятый
пункт записи наблюдением из готового HTML. КП с пропущенной проверкой цвета
к выдаче не готово.

Проверка HTTP полезна для интерфейса, но не подтверждает автономное открытие.
Отдельно открой `dist/<slug>/index.html` по `file://`, когда инструмент это
разрешает. Если браузерный инструмент блокирует `file:` политикой, не обходи
блок — назови этот критерий непроверенным, не выдавай HTTP-предпросмотр или
факт сборки за проверку офлайн-HTML.

## 5. Передать результат

Сообщи путь к HTML, выбранный архетип и его связь с единицей продажи, какие
названия и цены взяты из входа/прайса, какие бизнес-данные синтетические, и
список допущений из `summary.json`. Назови статус `file://`, если он
непроверен. Сборка не равна визуальной приёмке, публикации или push.
Кратко назови происхождение primary: «цвет кнопок сайта …» либо
«предложен … из палитры, потому что …». Не называй предложенный цвет фирменным.
