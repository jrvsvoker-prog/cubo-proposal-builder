# Пайплайн билдера: от вводных о компании к демо-интерфейсам

> **Текущее исполнение MVP, 21.09.** Техническая последовательность и точные
> команды — только в [agent-runbook.md](agent-runbook.md). Штатный скрипт
> создаёт готовый валидный `profiles/<slug>.json` из `summary.json`; профиль
> вручную не дополняют и не копируют из school/service. `--draft` сохранён
> только как технический исторический режим.
>
> Работают только `school` и `service`; шесть принятых шаблонов сохраняются,
> а Data View остаётся просмотром записей без действий. Новый архетип, изменение
> экранов, метрик или шаблонов не входят в сборку одного клиента. Независимый
> прогон другим исполнителем (task-17) остаётся открытым.
>
> Что уже работает: `company.brand.logo` встраивает локальный PNG/SVG как
> data URI (проверка внешних ресурсов SVG — task-13); `proposal.partner`
> включает пару «партнёр × клиент» в шапке обложки, `proposal.intro` и
> `proposal.estimate` персонализируют оболочку (task-21); `jobs` влияет на
> `dashboard.defaultMetrics`, а `result` историй с экранами 03/06 попадает в
> карточку и кабинет (task-22). Полный список читаемых полей — таблица
> runbook и [data-contract.md](data-contract.md).
>
> Промежуточные утверждения сводки, джобов и продолжения не обязательны
> (решение task-16): при достаточных вводных агент идёт до HTML без
> остановок; короткий вопрос — только при существенной неясности адресата,
> предмета предложения или бизнес-модели.
> HTTP-проверка не доказывает `file://`: при блокировке протокола политикой
> инструмента этот критерий указывают как непроверенный, без обхода.
> С 22.09 выбор primary — обязательный шаг 1.1 runbook: исследование бренда
> с записью источников, затем при необходимости согласованная запасная палитра.
>
> Остальная часть файла сохранена как историческое целевое описание и пример
> reasoning: упоминания `retail`/`education` как рабочих архетипов, YAML-
> сводки, ручного дополнения профиля и `build:all` для произвольного slug
> не описывают текущую реализацию. `jobs` задаёт выбор и порядок
> поддержанных метрик. В расчёте значений KPI участвуют `scale.monthlyDeals` и
> `offer.priceRange`: генератор пишет их в профиль, модель дашборда и
> аналитики считает по ним объём и суммы. Так же сформулировано в
> [agent-runbook.md](agent-runbook.md).

Как из сообщения в чате («Механика, автосервис, 4 точки, лого») получается
набор из шести осмысленных демо-экранов. Документ описывает продуктовую
логику билдера; техническая упаковка (проект-папка, скилл, сборка) — task-08.

Связанные документы: [LOGIC.md](LOGIC.md) — модель данных, архетипы, каркас
лендинга; [ui-rules.md](ui-rules.md) — канон визуального ядра;
[data-contract.md](data-contract.md) — поля сводки и профиля.

Два принципа, из которых всё следует:

1. **Агент решает смысл один раз — на шаге сводки и джобов.** Ниже по
   пайплайну решений нет: маппинг на экраны и генератор данных
   детерминированы. Это и защита от слопа: случайные решения возможны только
   в одной точке, которую человек проверяет глазами за 30 секунд.
2. **Каждое число и подпись на экране должны отвечать на вопрос «зачем это
   здесь» джобом ниши.** Нет джоба — нет блока. Это отличает «их бизнес на
   Cubo» от «типичный дашборд с их логотипом».

## 1. Пайплайн по шагам

```
ВХОД            РЕСЁРЧ            СВОДКА           ДЖОБЫ             МАППИНГ         ПРОФИЛЬ        СБОРКА
чат, вольный →  агент: сайт, →    «как я понял →   Job Stories →     инфа → экран →   profiles/ →    vite build
текст           поиск, допущения  бизнес» + показ  роли/метрики       блоки и          <slug>.json    → один HTML
                                  человеку                          приоритеты                      → чек-лист
```

### Шаг 0. Вход — чат, вольный текст

Из вводных определяем компанию и бизнес-модель, без анкеты:

- **Компания** — название (как писать в интерфейсах).
- **Ниша** — чем занимаются и на чём зарабатывают («детская школа»,
  «автосервис», «сеть кофеен»). Это главный вход: по нише выбирается
  единица продажи и архетип.
- **Primary** агент выясняет сам по обязательному шагу 1.1
  [регламента](agent-runbook.md#11-обязательно-определить-primary).
  Если менеджер уже задал цвет, использует его.

Опционально: сайт, логотип файлом, число точек/филиалов, город, «наша
особенность — …». Всё неуказанное агент добывает сам (шаг 1) или помечает
допущением (шаг 2).

**Приём лого — подготовка агентом до генерации.** Агент берёт переданный
или официальный исходник, проверяет фон и цвет, сохраняет пригодный PNG/SVG
в своём `runs/<slug>/`. В `company.brand.logo` сводки указывает относительный
путь; генератор встраивает файл в профиль. Для RAND поле `logo` не пишется:
шаблон инлайнится в шапке. Чужой интегратор — `proposal.partner.logo`.
Порядок выбора, удаления фона, отказа от неудачной инверсии и проверки —
в [регламенте](agent-runbook.md#логотип-клиента-и-партнёра). Менеджер не правит
JSON; отсутствие пригодного логотипа допускает штатный fallback.

Короткий вопрос человеку нужен только при существенной неясности адресата,
предмета предложения или бизнес-модели — например, если по входу нельзя
понять, **что является одной продажей** (чек? заказ? абонемент? сделка?).
Всё остальное агент предполагает сам, один уточняющий вопрос максимум;
заведомо неподходящий архетип ради отсутствия вопросов не выбирается.
Вопрос выясняет деятельность и предложение клиента, не предлагает выбор
между шаблонами Builder. После ответа подтверждённые сведения не переспрашивают;
до выдачи выполняют смысловую сверку по действующему runbook.

### Шаг 1. Ресёрч — агент добывает недостающее

Что агент ищет и откуда (порядок по убыванию ценности):

| Что | Источник | Куда ляжет |
|---|---|---|
| Реальные названия услуг/товаров и цены | сайт, прайс, меню | `offer.items`, `priceRange` → подборки, аналитика, карточка |
| Подразделения и как они называются | сайт («наши филиалы», адреса) | `units` → дашборд, датавью |
| Единица продажи и путь клиента | сайт + типовой сценарий ниши | `deal.noun`, `deal.pipeline` → датавью |
| Кто их клиент | сайт, тональность | `customer` → карточка, кабинет, подборки |
| Лого | переданный файл или официальный исходник | `company.brand.logo` |
| Primary | пожелание менеджера → брендбук → главная и профильная страница сайта → согласованная палитра при отсутствии подтверждённого цвета | явный `company.brand.primary` → `theme.primary`; источник и выбор в `research.md` |
| Сезонность ниши | здравый смысл + типовые профили | `time.seasonality` → генератор, график |
| Порядок величин | публичные данные, типовые значения ниши | `scale` → генератор |

Правило источников: **реальное берём только для названий и лексики**
(услуги, филиалы, продуктовые слова). Цифры с сайта (выручка, число учеников)
в интерфейс не подставляем — данные всегда демонстрационные, это прямо
написано в шапке КП. Реальные названия + вымышленные цифры = правдоподобие
без вранья.

Если сайта нет или он пуст — агент работает по типовой модели ниши и
помечает всё допущениями.

### Шаг 2. Сводка «как я понял бизнес»

Рабочий артефакт агента — YAML по формату LOGIC.md §2.3, дополненный блоком
`jobs` (шаг 3). Показывается человеку целиком: «так? / не так — поправь
две строки». Это единственная точка ручного контроля.

Правила сводки:

- Каждое поле, выведенное предположением, — `assumption: true` или пометка
  в списке допущений в конце.
- Названия услуг и филиалов — реальные, если сайт дал их; вымышленные
  правдоподобные — если нет (но помечены).
- `archetype` выбирается **по единице продажи**, не по отрасли: кофейня —
  `retail`, кулинарная школа — `education`. Архетип — это ближайший шаблон
  и отправная точка, **не жёсткая классификация**: новые ниши не требуют
  заведения архетипа заранее; при непопадании берётся ближайший, и это
  помечается допущением.

### Шаг 3. Продуктовый фреймворк — Job Stories ниши

Прежде чем маппить что-то на экраны, агент прогоняет нишу через фреймворк:
кто работает в этом бизнесе, что каждый хочет видеть и зачем. Шаблон — в
разделе 2, заполненный пример — в разделе 2.2.

Смысл шага: метрики и блоки перестают быть «типичными» — каждая отвечает на
конкретный джоб конкретной роли. Например, «заполняемость мест» у школы
существует потому, что у собственника есть джоб «When начинается учебный
год, I want to видеть, где пустуют группы, so I can докрутить набор до
октября». У автосервиса этой метрики нет — там джоб про загрузку постов.

Выход шага (добавляется в сводку как `jobs:`):

- **3–4 роли ниши** (по умолчанию: руководитель, менеджер/администратор,
  линейный сотрудник, клиент клиента).
- **1–3 джоба на роль** в формате `When … I want to … So I can …`.
- **Метрики-доказательства** — какое число показывает, что джоб выполнен.
- **Главный джоб** — один, определяет hero-метрику дашборда.

### Шаг 4. Маппинг на экраны

Из сводки + джобов по таблице раздела 3 выводится содержание каждого из
шести шаблонов. Механика шаблонов фиксирована (LOGIC.md §4) — меняется
только содержание. Правила приоритета — в разделе 3.2.

### Шаг 5. Профиль

Сводка → `src/data/profiles/<slug>.json` (все ключи — по образцу
`school.json`: hero, sections, entity, leads, selectionCourses, portal,
dashboard, analyticsConfig и т.д.).

**Черновик профиля пишет скрипт, не агент** (решение 10.09): генератор
«сводка → черновик профиля» заполняет все шаблонные ключи, агент только
дополняет свободные тексты (сообщения таймлайна, приветствия) и правит
неточности. Это защита от слопа: 600 строк JSON руками — главный источник
случайных решений. Скрипт — `scripts/profile-draft.mjs` (действует с 13.09:
машиночитаемая сводка JSON → `profiles/<slug>.draft.json` со слотами
`[ ЗАПОЛНИТЬ: … ]`); слои `generated` с числами по-прежнему пишет только
генератор дашборда.

Числа для дашборда и аналитики не пишутся вручную — их считает
`dashboard-model.ts` от `business`, `units`, `seed` (= slug компании:
пересборка даёт те же цифры).

Валидация: неизвестный `business`, пустые обязательные поля, дельты без
формулы — ошибка до сборки, а не молчаливая подстановка. Валидатор профиля
переносится в новую схему в рамках task-08.

### Шаг 6. Сборка и приёмка

`npm run build:all` → `dist/<slug>/index.html`. Прогон чек-листа раздела 5
на трёх ширинах (1440 / 1024 / 390), проверка открытия по `file://`
(localhost не подтверждает переносимость). Допущения — в ответе человеку
и в строке `assumptions` дашборда.

## 2. Шаблон Job Stories для ниши

### 2.1 Пустой шаблон (заполняет агент на шаге 3)

```yaml
jobs:
  main: <один джоб, который определяет hero-метрику дашборда>
  roles:
    - role: "Руководитель / собственник"
      stories:
        - when: "<ситуация/триггер>"
          want: "<что хочет увидеть/сделать>"
          so: "<зачем — решение или результат>"
          metrics: ["<метрика-доказательство>", ...]
          screens: ["01"]          # куда маппится, см. раздел 3
    - role: "Менеджер / администратор"
      stories: [ ... ]
    - role: "<линейный сотрудник ниши>"   # куратор, мастер, продавец, врач
      stories: [ ... ]
    - role: "<клиент клиента>"            # родитель, покупатель, заказчик
      stories: [ ... ]
```

Правила заполнения:

- **Джоб = ситуация, а не фича.** «When подошёл срок оплаты» — джоб;
  «хочу CRM» — нет.
- **У каждого джоба должна быть метрика-доказательство** из библиотеки
  архетипа (`dashboard-model.ts`) или новая с формулой. Джоб без метрики —
  повод убрать его или придумать честную формулу, а не показывать «красивое
  число».
- **Роль «клиент клиента» обязательна** — её джобы определяют экраны 05–06.
- 1–3 джоба на роль, всего 6–10. Больше — признак того, что агент пишет
  фичи-лист, а не джобы.
- Метрики «меньше — лучше» (долги, возвраты, повторные обращения, отмены)
  помечаются — они получают `debt: true` и инверсию пилюли.

### 2.2 Заполненный пример — `education` (школа «Среда»)

| Роль | Job Story | Метрики | Экран |
|---|---|---|---|
| Собственник сети | When закрывается месяц, I want to сравнить филиалы по поступлениям и долгу, so I can увидеть отстающий и разобраться | Поступления, Доля задолженности (debt) | 01, 02 |
| Собственник | When начинается учебный год, I want to видеть заполняемость групп по филиалам, so I can докрутить набор до октября | Заполняемость мест (snapshot) | 01 |
| Куратор | When родитель пишет в чат, I want to видеть всю историю ученика рядом с диалогом, so I can отвечать без поиска по системам | — (история, не число) | 03 |
| Куратор | When накопились заявки, I want to видеть их по стадиям с суммами, so I can понимать, кого двигать дальше | Заявки по стадиям | 04 |
| Администратор | When нужно предложить занятия, I want to отправить родителю подборку ссылкой, so I can получить отметки интересов без звонка | Открыли → отреагировали → заявка | 05 |
| Родитель (клиент клиента) | When подошла оплата, I want to видеть абонемент и следующий платёж в кабинете, so I can оплатить без звонка администратору | — | 06 |

Главный джоб — первый: hero-метрика дашборда «Поступления», метрика риска
«Доля задолженности» с `debt: true`.

## 3. Маппинг «информация → экран»

### 3.1 Таблица маппинга

| Что известно (поле сводки / джоб) | Куда попадает | Что именно показываем | Почему это убеждает |
|---|---|---|---|
| `units` — названия и число подразделений | 01 карточки-ряд; 02 фильтр; 04 колонка | Их реальные филиалы с разным «характером» цифр | Мгновенное узнавание: «это про нас» |
| `units.kind` — как называется единица | 01 подписи, 02 фильтры, тексты | «Филиал» / «точка» / «пост» в их терминах | Интерфейс говорит на их языке |
| `offer.items` — реальные услуги/товары | 02 разрез «направления»; 04 поле позиции; 05 позиции подборки; 03 поля карточки | Их прайс-лист внутри Cubo | Самый сильный персональный сигнал |
| `offer.priceRange`, `priceUnit` | 04 суммы; 05 цены; 03 оплаты | Правдоподобные суммы их порядка | Цифры «как у них», не миллионы ниоткуда |
| `deal.pipeline` — стадии продажи | 04 колонки пайплайна | Их путь клиента: «Новая → Пробный день → Договор → Оплачено» | Показывает, что Cubo ложится на их процесс |
| `customer.entity` — главная сущность | 03 карточка; 04 имя записи | «Ученик» / «заказ» / «пациент» с правдоподобными полями | Демонстрация глубины, не абстрактная «запись» |
| `customer.singular` + `entityExample` | 05 получатель; 06 приветствие | Живой персонаж: «Маша Ковалёва, 2 «Б», Арбат» | Экраны 05–06 смотрятся глазами их клиента |
| Главный джоб собственника | 01 набор `defaultMetrics` | Метрики джобов первыми в порядке упоминания, затем базовые архетипа | Дашборд отвечает на их вопрос, а не «вообще про деньги» |
| Метрики-риски (`debt: true`) | 01, 02 | Доля долга / возвратов / повторных с инверсией пилюли | Честность: меньше — лучше, и это видно |
| Джобы менеджера/линейного | 03, 04 | Группы полей карточки, стадии, «следующий шаг» в записях | Показываем работу команды, не только отчёты |
| Джобы клиента клиента | 05, 06 | Подборка с их позициями; кабинет с их сущностями | «Ваши клиенты получат вот это» |
| `time.seasonality` | 01, 02 графики | Провал лета у школы, пик декабря у розницы | График выглядит как их год, не как ровная линия |
| `scale` — порядок величин | все числа | Сотни платежей у школы, тысячи чеков у розницы | Нет «34,4 млн» у трёхкомнатного автосервиса |
| `brand.primary` | все экраны | `--client-primary` → акценты, активный пункт меню | Фирменный цвет — второй по силе сигнал после названий |
| `brand.logo` | 05 рамка подборки, шапка лендинга | Их лого там, где ссылку получают их клиенты | Правильная атрибуция: это их ссылка, не Cubo |
| `staffName/staffRole` | сайдбар, 03 авторы в таймлайне | «Анна Смирнова · Куратор» | Интерфейс населён, не стерилен |
| Джоб без экрана | — | Не показываем | Если джоб не ложится на механику шаблонов — оставляем в сводке, не изобретаем блок |

### 3.2 Правила и приоритеты

- **Граница дашборд/аналитика жёсткая** (LOGIC.md §4): 01 — сколько и где;
  02 — как менялось и из чего складывается. В дашборд графики и таблицы не
  добавляем, даже если джоб «просится».
- **Базовый набор дашборда** — из библиотеки архетипа; поддержанные метрики
  джобов идут первыми в порядке упоминания. Предела «ровно четыре» нет;
  произвольная метрика вне библиотеки недопустима.
- **Адаптация по числу единиц** (проверено): 0/1 — компактная сетка без
  «итога»; 2–6 — ряд + итог; 7+ — 3 карточки + итог с пагинацией.
- **Колонка «Подразделение» в 04 скрывается при `units = []`** — не
  показываем пустые измерения.
- **Приоритет правдоподобия выше полноты**: лучше 5 их реальных позиций,
  чем 8 выдуманных. Недостающее — допущение, не «Услуга 1».
- **Экраны 05–06 — глазами клиента клиента**: в рамке подборки их лого,
  обращение по `customer.singular`; разделитель «Для ваших клиентов» на
  лендинге обязателен.
- **Согласованность между экранами**: имена, позиции, суммы совпадают в
  03 → 04 → 05 → 06 (одна генерация, один источник).

## 4. Анти-слоп: правила генерации

Слоп здесь — это случайные решения, галлюцинированные данные и «типичный»
результат, не отличимый от шаблона. Правила по видам:

### 4.1 Честные числа

- Метрика существует только с формулой (библиотека `dashboard-model.ts`).
  Новая метрика = формула + `n`/`d` + пометка `debt` где «меньше — лучше».
- Дельты разноцветные: генератор гарантирует один растущий (~+12 %) и один
  проседающий (~−5 %) юнит. Все зелёные или все одинаковые — брак.
- Срезовые метрики (заполняемость, дебиторка) подписаны датой среза и не
  суммируются по месяцам — формулы это фиксируют.
- Структура/разрезы — с явным лидером (35/25/18/12/10), не поровну.
- Демо-данные помечены один раз в шапке («демонстрационные данные»), не в
  каждой карточке.

### 4.2 Правдоподобие

- Реальные названия — из ресёрча; вымышленные — в стиле ниши
  («Диагностика ходовой», не «Услуга 3»).
- Суммы внутри `priceRange`, порядок величин — из `scale`.
- Сезонность ниши в графике; `flat` только когда сезонности правда нет.
- Персонажи согласованы: ученик карточки = получатель подборки = ребёнок в
  кабинете родителя.
- Тексты таймлайна — живые и отраслевые (свободный слой), но без выдуманных
  фактов о компании («у вас было…» запрещено — только «например»).

### 4.3 Допущения

- Всё предположённое — `assumption: true` в сводке и перечислено в ответе
  человеку.
- В КП допущение звучит как «например», никогда как «у вас».
- Строка `dashboard.assumptions` обязательна: 2–3 прозрачных правила учёта
  («филиалы ведут раздельный учёт…»), а не отмазка.

### 4.4 Нехватка информации — что делать

| Нет… | Делаем |
|---|---|
| сайта | типовая модель ниши, всё помечено допущениями |
| primary | сначала обязательная проверка бренда по [runbook](agent-runbook.md#primary-и-монохромный-логотип); если цвет не подтверждён — один из пяти согласованных вариантов с допущением, без ориентиров синий `#0369a1`. Поле задаём явно, решение с доказательствами/ограничениями сохраняем в `research.md` |
| читаемого primary (кислотный/светлый) | автопроверки контраста нет — подбираем читаемую замену вручную, помечаем допущением |
| названий позиций | типовые позиции ниши, допущение; никогда «Позиция N» |
| числа подразделений | пустой `units.names`, показатели компании; отсутствие сведений не означает, что подразделений нет |
| порядка цен | типовой диапазон ниши, допущение |
| попадания в архетип | сопоставить единицу продажи с school/service; заведомо неподходящий шаблон не выбирать |
| понимания, что продают | единственный уточняющий вопрос (шаг 0) |

### 4.5 Запреты

- Не показывать механику, которой нет в шаблонах (не изобретать блоки и
  экраны под джоб).
- Не выдавать демо-цифры за реальные данные клиента.
- Не перекрашивать семантику success/danger под бренд; из бренда — только
  primary и лого.
- Не оставлять кнопки «в никуда»; демо-действия подписаны как демо (вход в
  кабинет, заявка, счёт).
- Не дописывать «мы изучили ваши процессы», если изучения не было.
- Управление демонстрацией — снаружи рамки экрана, не маскируется под
  функцию интерфейса (LOGIC.md §3a).

## 6. Формат результата билдера

Результат — проект-папка (модель — cubo-main), внутри:

```
app-cubo-showcase/
  AGENTS.md + скилл /proposal      # правила для агента: вход → сводка → джобы → профиль → сборка
  src/data/profiles/<slug>.json    # профиль компании (единственное, что меняется между клиентами)
  src/data/dashboard-model.ts      # генератор: метрики, характер юнитов, сезонность, сид
  src/components/…                 # шесть шаблонов на визуальном ядре
  dist/<slug>/index.html           # собранное КП — один файл для отправки
  docs/dynamic-proposal/           # этот пайплайн + LOGIC + ui-rules
```

Сценарий работы человека: открыть папку агентом → дать вводные в чате →
агент проходит шаги 0–5 → получить `dist/<slug>/index.html`.

**Принятое решение (10.09):** билдер — это «чат + проект-папка с правилами,
шаблонами интерфейсов и правилами дизайна». Отдельного приложения-
конструктора нет и не планируется; веб-форма — возможный следующий этап,
только если через чат получится хорошо.

## 7. Принятые решения (10.09)

Закрыты по решению пользователя, правила уже в тексте выше:

- **Генератор профиля — да, скриптом.** Черновик `profiles/<slug>.json`
  пишет скрипт «сводка → профиль», агент дополняет свободные тексты.
  Анти-слоп: ручные 600 строк JSON — главный источник случайных решений.
  Реализация — task-08.
- **Архетипы не фиксируются.** Архетип — ближайший шаблон, а не
  классификация; новые ниши не требуют заведения архетипа заранее.
  Непопадание = ближайший + допущение.
- **Лого принимает человек при сборке.** Механика «положил файл →
  подставилось»: файл в assets, имя в `brand.logo`, fallback — инициалы
  (шаг 0).
- **Контраст primary — без автопроверки.** Кислотный/светлый цвет —
  ручная замена на читаемый, допущением (§4.4).
- **Валидатор профиля — да.** Переносится в новую схему, часть task-08.
- **Формат билдера.** «Чат + проект-папка», отдельного приложения нет
  (§6).
