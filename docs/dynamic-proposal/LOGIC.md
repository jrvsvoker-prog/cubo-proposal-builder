# Динамическое КП Cubo — логика системы

## Уточнение пользователя · 09.09.2026, после обзора ворктри

Эта запись имеет приоритет над прежними ограничениями ниже.

- Агент может выбирать сценарий, метрики и композицию дашборда по вводным о
  компании и дополнительному поиску. Жёсткая привязка к Candy, одной нише,
  серому каркасу и фиксированной механике шаблона больше не требуется.
- Главный критерий — аккуратный, убедительный UI дашборда. Глубокая проработка
  UX и универсальная логика для всех компаний не являются условием перехода
  к визуалу. Правдоподобных демо-данных и работающих показанных действий достаточно.
- Primary-цвет клиента используем в интерфейсах. Авторский визуальный язык
  Cubo сохраняется; клиентская палитра не заменяет семантические цвета состояний.
- Оформление самого КП должно быть красивым, но это отдельная задача.
- Существующие профиль, генератор, архетипы и UX-прототипы — полезные наработки,
  а не обязательные ограничения нового экрана. Вход через чат и результат
  в виде проект-папки/собранного предложения сохраняются.

Разделы 0, 2.2, 4 и 10 ниже сохраняют историю прежнего подхода в части
фиксированной композиции, единственного шага LLM и обязательного UX-согласования.
Эти ограничения отменены данным уточнением. Новая UI-реализация ещё не начата.

Документ отвечает на один вопрос: **как из «название компании + чем занимается» получается
персональное интерактивное КП и по каким правилам оно адаптируется**. Визуал здесь не
обсуждается.

## Решения пользователя · 09.09.2026

Эти пункты закрыты и не обсуждаются повторно:

- **Глобальная картинка.** Результат работы — **проект-папка**, как cubo-main: внутри
  правила для агента (AGENTS.md + скилл), шесть шаблонов экранов, генератор данных,
  сборка. Человек подключается к папке агентом, даёт вводные в чате — получает HTML.
  Это и есть «система»; отдельного приложения-конструктора нет.
- **Вход — через чат, в любом виде.** Никакой формы или анкеты для человека. Агент сам
  ищет по сайту, сам додумывает недостающее и накладывает на наши интерфейсы.
- **Результат — примерная картинка,** «как бизнес клиента ложится на Cubo». Идеала
  нет и не нужно; предположения агента допустимы.
- **Веб-форма — не в плане.** Возможно, потом, если через чат получится хорошо.
- **Стиль — фиксированный, авторский (пользователя).** Цвета и стиль под клиента
  не адаптируем. Из бренда клиента — максимум логотип и праймари-цвет.

## 0. Главная мысль в трёх строках

1. **Нейронка решает смысл, код решает всё остальное.** Из вводных в чате агент сам
   пишет короткую сводку «как я понял этот бизнес» (~15 строк, раздел 2.3). Из сводки
   детерминированно (скриптом) выводятся профиль, данные, тексты и сборка шести экранов.
   Сводка — рабочий шаг агента, не форма для человека.
2. **Шесть экранов — это шесть шаблонов с фиксированной механикой и заменяемым
   содержанием.** Что фиксировано, а что меняется — определено для каждого экрана
   ниже (раздел 4). Нет «нейронка решает, какой сделать экран».
3. **Одна модель данных на все шесть экранов.** Цифры дашборда, аналитики, карточки,
   датавью, подборок и кабинета берутся из одного генератора с одними зёрнами, поэтому
   не противоречат друг другу.

## 1. Два разных «динамических»

| | Когда | Кто действует | Что меняется |
|---|---|---|---|
| **Подготовка** (генерация) | До отправки клиенту | Человек в чате + агент по правилам папки | Компания, сущности, метрики, тексты, данные, логотип |
| **Просмотр** (интерактив) | Клиент открыл ссылку | Получатель КП | Периоды, фильтры, виды, выбор в подборке, вход в ЛК |

Клиент **не видит** конструктора: ни выбора ниши, ни опросника. Он получает уже собранное
предложение. Всё управление демонстрацией (например, «Индивидуальная / Массовая» в
подборках) стоит снаружи рамки экрана и подписано как выбор примера, а не как функция
интерфейса.

## 2. Конвейер подготовки

```
 ЧАТ                  ПОНИМАНИЕ              СВОДКА                 ВЫВОД                    СБОРКА
 «Механика,      →    агент: сайт,      →    ~15 строк,       →     скрипт:            →     vite build
 автосервис,           поиск, свои            показать           профиль JSON              один HTML
 4 точки, лого»        предположения          человеку           + данные + тексты         (+ PDF позже)
```

### 2.1 Вход — чат, в любом виде

Человек пишет агенту что угодно: название, ссылку на сайт, пару фраз, логотип файлом.
Агент не задаёт анкету; если чего-то критичного нет (например, не понять, что продают) —
один уточняющий вопрос, иначе предполагает сам.

Правило: **предположения допустимы, но помечаются.** Всё, что агент вывел сам, в сводке
отмечено как предположение и в КП звучит как «например», а не «у вас». Точность
не цель — цель правдоподобная картинка «ваш бизнес на Cubo».

### 2.2 Понимание (единственный шаг, где работает LLM)

Агент читает сайт/описание, ищет в интернете и сам пишет сводку по фиксированному
списку пунктов (2.3). Именно здесь живёт «кусочек ресёрча», о котором говорили на
созвоне (07:05–07:25): без него получается механическая замена названия.

### 2.3 Сводка «как я понял бизнес» (рабочий артефакт агента)

Не форма. Агент пишет её сам и показывает человеку на 30 секунд: «так? / не так,
точек две». Дальше всё автоматически. Пример для школы:

```yaml
company:
  name: "Среда"                       # как называть в текстах
  displayName: "Школа «Среда»"
  activity: "Детская школа доп. образования"
  brand: { logo: url|null, accent: "#..."|null, site: "sreda.ru" }

archetype: education                  # см. раздел 3 — определяет наборы метрик/стадий
units:                                # подразделения. [] — нет; 1; несколько; много (>8)
  kind: "Филиал"                      # как называется единица: филиал / точка / магазин / офис / бригада
  names: ["Арбат", "Сокол", "Строгино"]
  assumption: true

customer:                             # клиент клиента — пользователь ЛК и получатель подборок
  singular: "Родитель"
  entity: "Ученик"                    # главная сущность карточки (03) и списка (04)
  entityExample: { name: "Маша Ковалёва", chips: ["2 «Б»", "Арбат"] }

offer:                                # что продают — позиции подборок (05), направления аналитики (02)
  itemNoun: "Занятие"
  items: ["Робототехника", "Шахматы", "Живопись", "Английский", "Подготовка к школе"]
  priceUnit: "₽ / мес."
  priceRange: [16800, 28000]

deal:                                 # единица продажи — «чек» дашборда и «запись» датавью
  noun: "Платёж"                      # платёж / чек / заказ / сделка
  pipeline: ["Новая", "Пробный день", "Договор", "Оплачено"]   # стадии для (04)

time:
  scales: ["month", "academic"]       # какие масштабы периода имеют смысл
  seasonality: "school"               # профиль сезонности для генератора (school / retail / flat / summer-peak)
  demoDate: "2026-09-08"

scale:                                # порядок величин для правдоподобных цифр
  monthlyDeals: 550                   # сделок в месяц на всю сеть
  avgDeal: 27000

tone:                                 # для текстов лендинга
  audience: "Собственник сети"
  formal: true
```

Человек **глядит на сводку** перед выводом («так / не так») — это единственная точка
ручного контроля, и она короткая. Всё, что ниже сводки — автоматически. Поле `brand`
здесь — только логотип и праймари-цвет; стиль экранов фиксированный (см. «Решения»).

### 2.4 Вывод профиля (детерминированный скрипт)

Из сводки + архетипа скрипт собирает то, что в v1 сейчас лежит в `profiles/school.json`
27 разрозненными ключами:

- **метрики дашборда** — 4 по умолчанию из библиотеки архетипа (раздел 3), названия
  единиц из `units.kind`, масштабы из `time.scales`;
- **данные** — генератор (раздел 5) от `scale`, `units`, `seasonality`;
- **тексты лендинга** — из шаблонных фраз с подстановкой `customer`, `offer`, `deal`
  (раздел 6), не отдельно выдуманные для каждого клиента;
- **сущности** — карточка из `customer.entity`, список из `deal.pipeline`, подборки из
  `offer.items`, кабинет из `customer.singular` + те же `offer.items`;
- **логотип клиента** — в рамках экранов и в шапке лендинга; праймари-цвет — по
  желанию, одной переменной. Больше из бренда ничего не берём.

Профиль проверяется валидатором (v1 уже так делает: неизвестный архетип или пустые
поля — ошибка сборки, а не подстановка другой компании).

### 2.5 Сборка и проверка

`vite build --mode <client-slug>` → один HTML. Перед отправкой — прогон чек-листа
(раздел 8) на трёх ширинах. PDF (когда понадобится) — печатная версия того же HTML:
статичные состояния каждого экрана, без интерактива. Отдельного PDF-шаблона не нужно.

## 3. Архетипы: что реально различается между бизнесами

Архетип — это **внутренняя заготовка агента**, не классификация клиентов. Агент
не может «показать выручку» без формулы, а формулы у бизнесов разные (заполняемость
у школы, средний чек у магазина, «в срок» у сервиса). Чтобы не изобретать формулы
каждый раз, лежат готовые наборы; агент берёт ближайший и переименовывает подписи под
клиента. Ничего страшного, если попадание примерное — результат и должен быть
примерной картинкой.

Архетип задаёт три вещи: библиотеку метрик, стадии пайплайна по умолчанию и профиль
сезонности. Всё остальное — из сводки.

Стартуем с трёх, которые уже есть в коде; остальные строки таблицы — кандидаты,
добавляются по факту, когда придёт клиент, который не ложится.

| Архетип | Единица продажи | Метрики по умолчанию (4 из 6) | Стадии по умолчанию | ЛК для кого |
|---|---|---|---|---|
| `education` (школы, курсы, секции) | платёж/абонемент | Поступления · Заполняемость · Доля долга · Средний платёж (+ Платежи, Ученики) | Новая → Пробное → Договор → Оплачено | родитель / ученик |
| `retail` (магазины, точки) | чек | Продажи · Средний чек · Конверсия · Доля возвратов (+ Чеки, Товаров в чеке) | Заказ → Собран → Выдан → Закрыт | покупатель (программа лояльности) |
| `service` (сервис, ремонт, ателье) | заказ | Выручка · Выполнено в срок · Загрузка · Средний заказ (+ Заказы, Повторные) | Заявка → Диагностика → В работе → Готово | заказчик |
| `b2b-deals` (агентства, юристы, консалтинг, Cubo сам) | сделка/проект | Выручка · Конверсия воронки · Средний чек · Дебиторка (+ Сделки, Средний цикл) | Лид → Квалификация → КП → Договор → Оплата | клиент-компания |
| `clinic-beauty` (клиники, салоны) | визит | Выручка · Загрузка кресел/кабинетов · Повторные визиты · Средний чек (+ Визиты, Отмены) | Запись → Подтверждена → Визит → Оплачено | пациент / гость |
| `hospitality` (отели, рестораны) | бронь/чек | Выручка · Загрузка · Средний чек · Отмены (+ Брони, RevPAR) | Бронь → Подтверждена → Заезд → Выезд | гость |

Первые три уже есть в `dashboard-model.ts` (как `Business`). Остальные — кандидаты;
**новый архетип = один файл с 6 метриками + стадии + сезонность**, ничего в экранах
не меняется. Если компания не ложится ни в один — берётся ближайший, и это помечается
в сводке как предположение.

Правило выбора: агент выбирает архетип по **единице продажи** («что у них является
одним чеком?»), а не по отрасли. Кофейня — `retail`, кулинарная школа — `education`.

## 3а. Каркас страницы КП (уровень выше экранов)

Зафиксировано по итогам UX-консультации 09.09 (последний ответ). Это внешняя оболочка,
в которой живут шесть экранов; она **одинакова для всех клиентов** и от сводки
получает только подстановки.

```
Шапка:      «Cubo»                                   «Для {displayName}»
Вход:       kicker · H1 · подзаголовок (три ответа: для кого, что показываем, что это демо)
            Оглавление-якоря: Показатели · Аналитика · Карточка · Данные · Подборки · Кабинет
01–04       ИНСТРУМЕНТЫ КОМАНДЫ   (дашборд, аналитика, карточка, датавью)
—— разделитель «Для ваших клиентов» ——
05–06       ИНТЕРФЕЙСЫ ДЛЯ КЛИЕНТОВ КЛИЕНТА   (подборки, кабинет)
Финал:      «Обсудим, как это применить в {displayName}» · [Связаться с Cubo]
```

Правила каркаса:

- **Вход короткий.** Не обложка на всю высоту: на десктопе в первом экране видны вводная
  часть и начало первого живого примера. Персонализация названа прямо («Для школы
  „Среда“»), но без «мы изучили ваши процессы», если этого не было.
- **Навигация — якорями, не переключением экранов.** Оглавление прокручивает к секции,
  не скрывая остальные; два пути равноправны — читать подряд или прыгнуть к нужному.
  Бокового меню нет (ширина — интерфейсам). Закреплять оглавление или нет — решаем на
  сером прототипе.
- **Граница ролей обозначена явно.** Получатель КП и пользователь внутри демонстрации —
  не один человек: в 01–04 он смотрит на инструменты своей команды, в 05–06 — на то,
  что получат его клиенты. Разделитель + подзаголовки вида «Так родители могут…».
  Без переключателя ролей и длинных объяснений.
- **Управление демонстрацией не маскируется под функцию интерфейса.** Переключатель
  «Индивидуальная / Массовая» стоит снаружи рамки с понятной подписью — это выбор
  примера, а не меню родителя.
- **Единый лейаут секции, разные лейауты внутри.** Номер и название → короткое
  объяснение пользы → строка возможностей → живой экран. Текст по центру, ограничен по
  ширине; экран — на всю ширину блока. Одинаковая внешняя ширина не значит одинаковую
  высоту или компоновку внутри: примеры не превращаем в одинаковые плитки.
- **Скролл один — страницы КП.** Не запираем примеры в одинаковые невысокие контейнеры
  с собственной прокруткой. Локальный скролл допустим у таймлайна, длинного списка,
  таблицы, пайплайна — когда он нужен самому сценарию.
- **Каждый пример содержателен до первого клика.** Нельзя требовать сначала выбрать
  период или заполнить поля, чтобы увидеть, что демонстрируется.
- **Примеры самостоятельны, но согласованы по содержанию.** Имена и данные не
  противоречат друг другу, но выбор курса в подборке не создаёт ученика в карточке и не
  пересчитывает дашборд — это уже другая глубина продукта.
- **Управление действует локально.** Период дашборда не меняет остальные пять секций;
  прокрутка к другому примеру не сбрасывает сделанный выбор; общего фильтра над всем
  КП нет.
- **Демо-действие отличается от настоящего.** В кабинете не просим реальные учётные
  данные; демонстрационная заявка не изображает отправку. Контакт с Cubo в финале —
  отдельное, явно названное действие.
- **Дашборд и аналитика не дублируют друг друга.** Дашборд — сравнить основные
  результаты (показатели, подразделения, период и база). Аналитика — разобрать
  результат (динамика, состав, разрез, детализация). В дашборд графики и таблицы не
  добавляем; понимать первый без второго должно быть можно.

## 4. Шесть экранов: что фиксировано, что выводится, что свободно

Для каждого экрана три слоя. **Механика** не меняется никогда (это и есть демонстрация
возможностей Cubo). **Выводится** — из карты автоматически. **Свободно** — одна-две
строки текста, которые может дописать человек.

### 01 Дашборд — «сравнить результаты сети и подразделений»

| Слой | Содержание |
|---|---|
| Механика | Секции показателей → внутри ряд карточек подразделений + итог сети. Период / масштаб / база сравнения. Выбор показателей (модалка). Итог всегда по всей сети, показ карточек его не меняет. |
| Выводится | Набор метрик (архетип), названия единиц (`units.kind`), масштабы (`time.scales`), стартовый период (последний завершённый), цифры (генератор). |
| Свободно | Строка `assumptions` («филиалы ведут раздельный учёт…»). |

**Адаптация по числу подразделений** (проверено в v1, сохранить):
- `units = []` или 1 → компактная сетка метрик 2×2 или 3×2, без «итога» (нечего суммировать), название единственной точки — в общем контексте, а не в карточке.
- 2–6 → ряд карточек + итог, всё видно без пагинации.
- 7+ → показывать 3 карточки + итог; «Карточки для сравнения» — выбрать какие ставить рядом; пагинация синхронна по всем секциям. Ручного изменения охвата итога нет (ревью: непрозрачное состояние).

**Адаптация по масштабу:** `education` — месяц + учебный год; `retail` — день/неделя/месяц/год; `service`, `b2b` — неделя/месяц/квартал/год. Срезовые метрики (заполняемость, ученики, дебиторка) подписываются датой среза на уровне секции, а не в каждой карточке.

### 02 Аналитика — «разобрать результат подробнее»

| Слой | Содержание |
|---|---|
| Механика | Табы Обзор / Продажи / Деньги. Фильтры: период, сравнение, подразделения, источники. KPI-строка → график динамики (две линии: текущий и база) → структура по разрезу → таблица → детализация по клику. |
| Выводится | Разрезы: `units`, `offer.items` (направления), источники (константы: сайт/соцсети/рекомендации/реклама), программы (если архетип имеет — абонемент/разовое). Подписи: `deal.noun` → «Платежи / Чеки / Заказы». Цифры — из тех же месячных счётчиков, что и дашборд. |
| Свободно | `moneyNote` (пояснение про учёт). |

Граница с дашбордом: дашборд — *сколько и где*, аналитика — *как менялось и из чего складывается*. В дашборд графики не добавляем.

### 03 Карточка сущности — «данные и история вместе»

| Слой | Содержание |
|---|---|
| Механика | Слева широкая история CuboTimeline: события, сообщения, задачи и поле ввода. Справа компактный список свойств. Шапка с именем и действиями отдельно. Задачу можно завершить и возобновить. |
| Выводится | Сущность = `customer.entity`. Один список `entity.properties`: состав и порядок выбираются под нишу и клиента, значения — из сводки и демо-данных. Подпись + значение; статус тегом, телефон/email ссылкой, остальное текстом. Обязательных групп и прогрессов нет. События таймлайна — 6–8 по шаблону: создана → первый контакт → изменение → задача выполнена → сообщение → задача открыта. |
| Свободно | Нужные свойства, их порядок, подписи и значения; текст сообщений под отрасль. Способ отображения выбирается из общего набора text/status/link. |

Не делаем связанную модель (карточка не «знает» о подборках). Достаточно совпадения имён.

### 04 Датавью — «один набор, три вида»

| Слой | Содержание |
|---|---|
| Механика | Переключатель Пайплайн / Таблица / Карточки. Один массив записей во всех трёх видах. В пайплайне — колонки-стадии со суммой. |
| Выводится | Стадии — `deal.pipeline`. Записи (10–12): имя (`customer.entity`), позиция (`offer.items`), подразделение (`units`), сумма (`priceRange`). Колонка «Подразделение» скрывается при `units = []`. |
| Свободно | — |

### 05 Подборки / КП-ссылка — «клиенту ровно то, что нужно»

| Слой | Содержание |
|---|---|
| Механика | Две демонстрации по переключателю снаружи рамки: индивидуальная (список позиций, сердечки, счётчик, кнопка «подготовить») и массовая (та же ссылка многим + статистика воронки рассылки). Логотип компании-клиента в рамке (это её ссылка родителям), стиль — наш. |
| Выводится | Позиции — `offer.items` с ценами; получатель — `customer.entityExample`; обращение — по `customer.singular`; массовая статистика — 4 числа генератора (отправлено → открыли → отреагировали → заявка). |
| Свободно | Вводная фраза подборки. |

Это механика Parure (индивидуальная/массовая подборка): ссылку получают клиенты клиента, поэтому в рамке логотип компании, а не Cubo. Цвета и стиль не меняются.

### 06 Личный кабинет — «клиент видит всё сам»

| Слой | Содержание |
|---|---|
| Механика | Экран входа (демо-вход без реальных данных) → кабинет: приветствие по имени, 3–4 блока (объекты, ближайшее событие, оплата, документ/счёт). |
| Выводится | Пользователь — `customer.singular` с именем из `entityExample`; блоки по архетипу: `education` — дети / ближайшее занятие / абонемент / домашнее задание; `service` — заказы / статус / счёт / акт; `b2b` — проекты / ближайшая встреча / счёт / договор. |
| Свободно | Приветственная фраза. |

Секции 05–06 отделены на лендинге разделителем «Для ваших клиентов»: получатель КП должен понять, что теперь смотрит глазами своего клиента.

## 5. Модель данных: один генератор на всё

Причина, почему цифры v1 выглядят фальшиво (34,4 / 34,3 / 34,2 млн; +4,8 / +5,1 / +4,9 %):
формулы дают всем единицам почти одинаковые значения, без характера.

Правила генератора:

1. **Зёрна из карты:** `monthlyDeals`, `avgDeal`, число единиц, сезонность.
2. **Характер подразделений:** каждому — множитель объёма (0,6–1,5) и множитель тренда
   (одно растёт ~+12 %, одно проседает ~−5 %, остальные около нуля). Тогда дельты
   разноцветные и есть что сравнивать.
3. **Характер направлений (`offer.items`):** распределение долей по убыванию с явным
   лидером (35 / 25 / 18 / 12 / 10 %), а не поровну.
4. **Сезонность** — профиль по месяцам: `school` (провал июль–август, пик сентябрь),
   `retail` (пик декабрь), `flat`, `summer-peak`.
5. **Один источник для всех экранов:** дашборд и аналитика читают одни месячные
   счётчики (v1 это уже проверяет тестом). Датавью, карточка, подборки и ЛК берут
   имена/цены/суммы из тех же `offer.items` и `priceRange`.
6. **Детерминированность:** сид = slug компании. Пересборка даёт те же цифры;
   у другой компании — другие.
7. Демо-данные явно помечены («демонстрационные данные») в шапке лендинга один раз,
   не в каждой карточке.

---

## 6. Тексты лендинга: шаблоны, не сочинение

Хиро и подзаголовки шести секций **не** пишутся нейронкой с нуля для каждого клиента
(в v1 они лежат в JSON — 30 строк ручного текста на компанию). Схема: фраза-шаблон с
подстановками из карты.

```
Kicker:    «Для {displayName} · демонстрационные данные»
H1:        «Ваши процессы. Возможности Cubo.»                     — константа
Подзаг.:   «{Метрика1} {units.kind-мн.}, работа с {entity-мн.} и кабинет {customer-мн.} — на примерах вашей отрасли.»

01: «Дашборд под задачи вашей команды» · meta: Периоды · Сравнение {units.kind-мн.} · Настройка показателей
03: «Карточка {entity-род.}: основные поля и история взаимодействий»
05: «Так {customer-мн.} могут посмотреть предложенные {offer.itemNoun-мн.} и отметить интересующие»
06: «Вход, приветствие и главные данные — в кабинете {customer-род.}»
```

Склонения — таблицей в карте (`customer.forms: {nom, gen, pl}`), заполняет LLM один
раз. Свободный текст — только там, где отмечено «Свободно» в разделе 4.

## 7. Адаптация при просмотре (responsive)

Правила, а не «как получится». Три контрольные ширины: 1440 / 1024 / 390.

| Экран | 1440 | 1024 | 390 |
|---|---|---|---|
| Лендинг | текст по центру ≤ 720 px, рамка на всю ширину 1200 | то же | рамка без «браузерной» шапки, отступы 16 |
| 01 Дашборд | ряд: итог + N карточек | итог + 2 карточки, остальные — пагинация | карточки 2 в ряд (как в Candy), тулбар складывается в одну колонку, дельта переносится под значение — **не поверх «базы»** (баг v1) |
| 02 Аналитика | фильтры в строку, график + структура | фильтры в 2 строки | KPI 2×2, график с горизонтальным скроллом, таблица → карточки |
| 03 Карточка | история слева, свойства справа (28%, минимум 240px) | две колонки | одна колонка: свойства → история; без экспандеров |
| 04 Датавью | пайплайн 4 колонки | 4 колонки с горизонтальным скроллом | по умолчанию открываются карточки, пайплайн — скроллом |
| 05 Подборки | центрированная колонка 720 | то же | на всю ширину |
| 06 ЛК | форма 400 по центру | то же | на всю ширину |

Общее: скролл — один, страницы КП; внутренний скролл у таймлайна, длинной панели свойств карточки, таблиц и
пайплайна. Переключатель мобильного вида на лендинге не делаем — просто открываем с
телефона.

## 8. Чек-лист перед отправкой клиенту (выход конвейера)

1. Сводка показана человеку; все предположения звучат в КП как примеры.
2. Название компании нигде не заменено «Средой» (грепом по HTML).
3. Дельты дашборда разноцветные; хотя бы одна единица в минусе.
4. Аналитика: две линии графика различимы; структура — с явным лидером.
5. Имена/позиции совпадают между 03 → 04 → 05 → 06.
6. Три ширины отсмотрены скриншотами; консоль чистая.
7. Нет кнопок, ведущих «в никуда» (PDF скрываем, пока не реализован).

## 10. Порядок работ — по экранам, не по слоям (решение пользователя 09.09)

Идём по одному экрану: **логика → адаптация → UX → визуал**. Первый — дашборд. Его
вылизанный визуал становится языком UI для остальных пяти; их UX и адаптив потом так же
точечно, по одному.

### Шаг 1. Дашборд

1. **Логика.** Что из сводки попадает в дашборд: набор метрик (из архетипа), единицы
   (`units`), масштабы периода (`time.scales`), зёрна цифр. Что фиксировано, что
   выводится — раздел 4/01. Генератор с характером (раздел 5) — только в части,
   которую читает дашборд.
2. **Адаптация.** Матрица состояний, каждое — живое, переключается пилюлей:
   подразделения 0 / 1 / 3 / 20 × масштаб (месяц / учебный год / неделя / год) ×
   ширина 1440 / 1024 / 390. Проверяем, что каждое состояние читается без объяснений.
3. **UX.** Начальное состояние → основное действие (сменить период, поставить
   подразделения рядом) → результат → возврат. Уже решено в UX-ревью: итог всегда
   по всей сети, нет ручного охвата, даты срезов на уровне секции, компактная сетка
   при 0/1, синхронная пагинация при 7+.
4. **Визуал.** Только после утверждения 1–3. Ориентир — Candy-структура на токенах
   Cubo; авторский стиль пользователя.

### Шаги 2–6. Остальные экраны

Аналитика → карточка → датавью → подборки → кабинет. Для каждого тот же цикл, но UI
берётся из дашборда (шаг 1.4), поэтому визуальный этап короче. Порядок можно менять по
приоритету показа.

### Параллельно, малыми кусками

Сводка и скрипт вывода профиля (2.3–2.4) растут вместе с экранами: на шаге 1 в сводке
только то, что нужно дашборду; каждый следующий экран добавляет свои поля. Скилл
`/proposal` собирается в конце, когда все шесть экранов умеют читать сводку.

## Статус

Прежняя логика реализована частично и сохранена как техническая наработка.
Актуальное направление — уточнение в начале документа: свобода выбора дашборда,
приоритет UI и primary клиента. Обязательный цикл раздела 10 больше не действует.
Оформление самого КП выполняется отдельной задачей.
