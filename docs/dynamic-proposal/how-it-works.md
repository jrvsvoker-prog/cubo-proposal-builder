# Динамическое КП Cubo — как это устроено

Короткая версия для показа: что мы делаем, как оно работает под капотом и где
мы сейчас. Подробности — в `builder-pipeline.md` (продуктовая логика генерации),
`LOGIC.md` (модель данных и шаблоны экранов), `ui-rules.md` (канон визуала).
Состояние на 11 сентября 2026.

## Что это

Персональное интерактивное коммерческое предложение: потенциальный клиент
открывает ссылку и видит **свой бизнес в Cubo** — свои филиалы, свои услуги,
своих клиентов, свой фирменный цвет. Не слайды про систему, а шесть живых
экранов, по которым можно кликать: менять период, фильтры, смотреть детали.

Вход — сообщение в чате менеджера («Детская школа „Среда“, четыре филиала,
вот сайт и лого»). Выход — один HTML-файл, который открывается без сервера.
Анкеты и конструктора нет ни у менеджера, ни у клиента.

## Два разных «динамических»

| | Когда | Кто действует | Что меняется |
|---|---|---|---|
| **Подготовка** | до отправки | менеджер в чате + агент по правилам проекта | компания, сущности, метрики, тексты, данные, лого |
| **Просмотр** | клиент открыл ссылку | получатель КП | периоды, фильтры, виды, выбор в подборке, вход в кабинет |

Клиент не видит кухни: ни выбора ниши, ни опросника — только собранное
предложение. Всё, что управляет демонстрацией (например «индивидуальная /
массовая подборка»), стоит снаружи рамки экрана и подписано как пример.

## Под капотом: конвейер

```
ЧАТ            РЕСЁРЧ           СВОДКА                ДЖОБЫ            ПРОФИЛЬ          ДАННЫЕ            СБОРКА
вольный   →    сайт, прайс,  →  «как я понял    →     Job Stories  →   JSON компании →  генератор      →  один HTML
текст          допущения        бизнес», ~15 строк    роли/метрики     (скриптом)       от сида           + чек-лист
                                ← человек проверяет →
```

Два принципа, на которых всё держится:

1. **Нейронка решает смысл один раз, дальше работает код.** Единственное
   место, где агент «думает», — сводка «как я понял бизнес» и джобы ниши.
   Человек проверяет её глазами за полминуты. Ниже по конвейеру решений нет:
   маппинг на экраны и генерация данных детерминированы. Пересборка с тем же
   входом даёт тот же результат.
2. **Каждое число на экране отвечает на вопрос «зачем оно здесь».** Метрика
   существует, только если у какой-то роли в этом бизнесе есть джоб, который
   она доказывает. Нет джоба — нет блока. Так «их бизнес в Cubo» отличается от
   «типичный дашборд с их логотипом».

Что делает каждый шаг:

- **Ресёрч.** Агент берёт с сайта названия услуг, филиалов, лексику ниши.
  Цифры с сайта в интерфейс не попадают никогда — данные всегда
  демонстрационные, об этом написано в шапке КП. Реальные названия +
  вымышленные цифры = правдоподобно и без вранья.
- **Сводка.** Один рабочий артефакт: единица продажи, подразделения, услуги,
  сезонность, порядок величин, бренд. Всё предположённое помечено как
  допущение и в текстах КП звучит как «например», никогда как «у вас».
- **Job Stories.** 3–4 роли (руководитель, администратор, линейный сотрудник,
  клиент клиента), 1–3 джоба на роль в формате «когда … хочу … чтобы …», у
  каждого — метрика-доказательство. Главный джоб задаёт hero-метрику дашборда.
- **Профиль.** Черновик JSON пишет скрипт, агент дополняет только живые тексты
  (скрипт — задача гейта 4; сегодняшние два профиля собраны руками по контракту).
  Валидатор не пропустит неизвестную нишу или метрику без формулы.
- **Данные.** Один генератор на все шесть экранов: числа дашборда, аналитики,
  карточки, подборок и кабинета не противоречат друг другу. Сид — имя компании.
- **Сборка.** `vite build` → `dist/<компания>/index.html`, проверка на трёх
  ширинах и открытие по `file://`.

## Пример джобов — школа «Среда»

| Роль | Job Story | Метрика | Экран |
|---|---|---|---|
| Собственник сети | Когда закрывается месяц, хочу сравнить филиалы по поступлениям и долгу, чтобы увидеть отстающий | Поступления · Доля задолженности | 01, 02 |
| Собственник | Когда начинается учебный год, хочу видеть заполняемость групп, чтобы докрутить набор до октября | Заполняемость мест | 01 |
| Куратор | Когда родитель пишет, хочу видеть историю ученика рядом с диалогом, чтобы отвечать без поиска | история | 03 |
| Куратор | Когда накопились заявки, хочу видеть их по стадиям с суммами, чтобы понимать, кого двигать | заявки по стадиям | 04 |
| Администратор | Когда нужно предложить занятия, хочу отправить родителю подборку ссылкой, чтобы получить отметки интереса без звонка | открыли → отреагировали → заявка | 05 |
| Родитель | Когда подошла оплата, хочу видеть абонемент и следующий платёж, чтобы оплатить без звонка | — | 06 |

Метрики «меньше — лучше» (долг, возвраты) помечены и показываются с
инверсией: рост долга — красный, снижение — зелёный.

## Шесть экранов = шесть шаблонов

Механика каждого экрана зафиксирована (это и есть демонстрация возможностей
Cubo), содержание выводится из профиля, одна-две строки текста свободны.

| Экран | Вопрос, на который отвечает | Что подставляется из профиля |
|---|---|---|
| 01 Дашборд | сколько и где | метрики архетипа, названия единиц, масштабы, цифры |
| 02 Аналитика | как менялось и из чего складывается — Динамика / Структура / Деньги | разрезы: филиалы, услуги, источники, программы |
| 03 Карточка сущности | данные и история вместе | сущность («ученик», «заказ»), группы полей, события |
| 04 Датавью | один набор записей, три вида: пайплайн / таблица / карточки | стадии продажи, позиции, суммы |
| 05 Подборки | клиенту клиента — ровно то, что ему нужно, ссылкой | позиции с ценами, получатель, лого компании в рамке |
| 06 Кабинет | клиент видит всё сам | человек, объекты, ближайшее событие, оплата |

Экраны 05–06 отделены разделителем «Для ваших клиентов»: получатель КП
понимает, что дальше смотрит глазами своего клиента.

## Дизайн: одно визуальное ядро

Источник стиля — дашборд; остальные экраны собраны на его языке, канон
записан в `ui-rules.md` и проверяется при локе каждого экрана:

- серые карточки-поверхности с белыми внутренними блоками, крупные числа с
  табличными цифрами, честные дельты-пилюли;
- из бренда клиента берём только primary и лого — акценты и активный пункт
  меню перекрашиваются, семантика успеха/ошибки нет;
- один стиль контролов на всех фонах, табы разделов одинаковые на всех
  экранах, любая модалка — общий примитив;
- никаких hex-цветов в интерфейсе — только токены дизайн-системы Cubo.

## Защита от «слопа»

Слоп — это случайные решения, выдуманные факты и результат, не отличимый от
шаблона. Правила: метрика только с формулой; дельты разноцветные (всегда есть
кто-то в минусе); структура с явным лидером, а не поровну; сезонность ниши в
графике; персонажи согласованы между экранами (ученик карточки = получатель
подборки = ребёнок в кабинете); допущения перечислены; демо-действия
подписаны как демо. Чек-лист — `builder-pipeline.md` §5.

Работа идёт гейтами; каждый гейт закрывается тегом на коммит.

| Гейт | Что | Статус |
|---|---|---|
| 0 | порядок в проекте, один индекс задач | готово |

| 4 | генератор: ручной прогон на третьей компании → скрипт → скилл → e2e | после 2 и 3 |

## Как посмотреть

Из `app-cubo-showcase/`: `npm ci`, затем `npm run dev -- --host 127.0.0.1
--port 5215 --strictPort` (сервис: `--mode service`). Лендинг с шестью экранами
— `/`, варианты страницы КП — `/proposal.html`, стенд дашборда — `/stand.html`.
Сборка и проверки: `npm run build:all` → `dist/school/`, `dist/service/`.
